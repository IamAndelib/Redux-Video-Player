## Goal
Asked for by the maintainer (2026-10-24): check automatically, on any machine with a GPU, that the player decodes
video on the GPU where the GPU supports the codec, falls back cleanly where it doesn't, and plays without dropped
frames or errors. Until now this was one hand check in M0.7 (Intel iHD, inside the Flatpak).

## Research (T1)
Probe on SKYNET (AMD RX 5500, Navi 14, Mesa 26.2.5 radeonsi), in the dev container:
- `vainfo` decodes H.264 (CB, Main, High), HEVC Main and Main10, VP9 profiles 0 and 2; no AV1 (RDNA1).
- `--vout=dummy` can't take GPU frames: VLC logs `vout: none found` after `trying format vaapi` and silently decodes
  in software. A real check needs an OpenGL output.
- In `kwin-session.sh` with GPU OpenGL (without `LIBGL_ALWAYS_SOFTWARE`), `--vout=gl` played 4K HDR10 HEVC and
  1080p H.264 through VA-API: `vaapi generic: Using Mesa Gallium driver …`, `4cc VAOP` in the video output format,
  `using glinterop module "glinterop_vaapi"`; 0 dropped or late frames, 0 errors. No crash: #73 needs software GL with
  a GPU visible.

Researcher report (T1), adopted as R1, our own script:
- **VLC's signals** (verified in this tree):
  - Hardware decoding: `vaapi generic: Using <driver>` (`modules/codec/avcodec/vaapi.c`) and
    `using glinterop module "glinterop_vaapi"`.
  - Dropped frames: `picture is too late to be displayed` (`src/video_output/video_output.c`, one per lost
    picture); late but shown: `picture displayed late`.
  - VLC doesn't log its software fallback (`video.c`); it shows as no `Using` line and the decoder module that won.
  - Decoder order: the hardware-only `ffmpeghw` (priority 10001) beats dav1d (10000), so AV1 goes to the GPU where it
    can, else to dav1d. The frame counters (`input_stats_t`) are only reachable through the CLI, Lua or libvlc, and
    the first two are cut (D20), so the check reads the log.
- **Independent evidence from the kernel:** the GPU's video-decode engine time per client
  (`/proc/<pid>/fdinfo`, `drm-engine-dec` on amdgpu; other drivers name it differently) must grow while a clip plays
  on the GPU.
- **Capabilities drive expectations** (the idea of Intel's vaapi-fits): `vainfo`'s decode (`VLD`) profiles decide
  per clip whether the GPU or software is expected.
- **Not adopted:** fluster (decoder conformance by frame checksums; VLC's OpenGL output can't dump frames) and a
  libvlc harness for exact counts (not the real app; the log is enough).
- **Clips:** generated by Debian's FFmpeg (x264, x265, libvpx-vp9, SVT-AV1, mpeg2video), 8 s of 1080p30, never the
  2 s matrix clips. No VC-1 encoder exists; VC-1 is left out (rare, and the matrix covers its decoding).

## Plan (T2)
- `redux/qa/hw-clips.tsv`: clip name, the VA-API profile it needs, FFmpeg encoder options. H.264 8- and 10-bit, HEVC
  8- and 10-bit, VP9 profiles 0 and 2, AV1 8- and 10-bit, MPEG-2.
- `redux/qa/l2-hw.sh`, run by `qa.sh` L2:
  - Skips the whole check (one `l2.hw` skip) without a render node (G27) or without VA-API decode profiles.
  - Otherwise generates missing clips (`build/hw-clips/`) and plays each in `kwin-session.sh` with GPU OpenGL
    (`REDUX_SESSION_GPU=1`): `vlc-static -I dummy --vout=gl -vv --play-and-exit`.
  - Results `l2.hw.<clip>`:
    - Expected on the GPU: pass when VLC logs both hardware lines, the decode engine's time grows (where the driver
      reports it), no picture is dropped, the log has no problems and the player exits 0.
    - Expected in software: the same without the hardware lines; the detail names the decoder that won.
  - `l2.hw.cpu`: the HEVC 10-bit clip again with `--no-hw-dec`; the detail reports both CPU times. Reported, not
    gated: CPU time is noisy.
- `kwin-session.sh`: `REDUX_SESSION_GPU=1` keeps hardware OpenGL (the default stays software, D30).
- Acceptance: on SKYNET every GPU-supported clip passes on the GPU and the rest fall back; a mutation run with
  `--no-hw-dec` makes the GPU clips fail; CI reports one `l2.hw` skip.
